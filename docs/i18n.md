## Context

The client wants the site to rank in English, Malay and Chinese, with every piece of content
translated. The translation is keyword-led, not literal: each page targets the variant people
actually search in that language, and where no volume exists, the term the competitor gap
analysis finds competitors and searchers using.

Why it is worth it (measured 2026-10-03):
- **Malay demand is real and unserved.** Ubersuggest MY/ms: `dapur gas` 5,400/mo, `ketuhar`
  1,300, `hood dapur` 720, `dapur gas terbaik` 590, `mesin basuh pinggan` 140. Page one for
  `hood dapur` and `hood dapur tanpa tebuk dinding` is social posts and Indonesian shops, no
  brand guide.
- **Chinese demand exists; Ubersuggest barely measures it.** It returns 抽油烟机 390/mo and
  净水器 320/mo, and nothing for 油烟机, 燃气灶, 煤气炉, 炉头, 洗碗机, 蒸烤箱, 烤箱. Page one
  for 抽油烟机 马来西亚 is Lazada, Shopee, a SENZ YouTube video, a Chinese-language supplier
  directory and Facebook videos (one a VATTI dealer's). No brand, Fotile included, has
  Chinese pages. So Chinese term choice is mostly competitor-gap based, per the brief.
- **Malaysians also search English loanwords in Malay context**: `cooker hood` 2,900/mo in
  the Malay data. The Malay keyword map must test the loanword against the Malay term
  every time, not assume the Malay word wins.

Decided with the user (2026-10-03):
- URLs: English unchanged (URL contract). `/ms/` with **localised Malay slugs** for
  categories and articles; `/zh/` keeps English slugs (Chinese slugs percent-encode badly
  when shared). Products, stores and static pages keep their English slug in both.
  Concretely, data-driven slugs localise and folder names do not:
  - `/ms/hood-dapur/` is the kitchen hood category.
  - `/ms/panduan-membeli/hood-dapur/` is an article (section and leaf both Malay).
  - `/ms/category/panduan-membeli/` is the archive. The `category` folder stays English.
  - `/ms/about-us/` is a static page.
- The two Malay guides move to `/ms/panduan-membeli/hood-dapur/` and
  `/ms/panduan-membeli/hood-dapur-tanpa-tebuk-dinding/`, with 301s from today's paths. The
  "Also in Malay" lines in three English bodies come out; hreflang and the switcher replace
  them. Each guide gets an English and a Chinese counterpart, written to the same outline,
  so the three form a real hreflang set.
- Publish translations indexable as they ship; client reviews after; fixes are SQL edits.
- Simplified Chinese only.
- Rollout: infrastructure, then money pages, then products, then articles by traffic, then
  static pages, store template and recipes.
- Store pages: template translated, dealer names and addresses as written.
- eWarranty: form translated; the email to staff stays English and states the language used.

## Architecture

### Routing: two root layouts, one set of views

Nothing today handles locale. `<html lang>` is fixed in `src/app/layout.tsx`. No slug,
redirect or legacy URL starts with `/ms` or `/zh`. A second dynamic segment cannot sit
beside `[slug]` (noted at `src/app/[slug]/[article]/page.tsx` L28-30).

- `src/app/(en)/…`: the current tree, moved into a route group with its own root layout
  (`lang="en-MY"`). URLs are unchanged, because route groups do not add a path segment.
- `src/app/(intl)/[locale]/…`: second root layout. `generateStaticParams` →
  `ms`, `zh`; `dynamicParams = false`; `<html lang>` is `ms-MY` / `zh-Hans-MY`. The
  route files mirror `(en)`: home, `[slug]`, `[slug]/[article]`, `category/[slug]`,
  `store/[slug]`, the static pages.
- Page logic moves out of the route files into views that take `locale`, so both trees
  are thin wrappers. `CategoryView` already works this way. No middleware and no i18n
  dependency; every page stays static.
- Switching language crosses root layouts, so it is a full page load. That is acceptable for
  a language switch.

### Data: translations in the same tables

- **Rows that already belong to a page get a `lang` column**, default `en-MY`, joined into
  their primary key. That is `category_guide`, `category_reason`, `category_faq`,
  `product_feature`, `product_faq`, `product_spec` (raw_text only), `product_dimension`
  labels and `product_video` metadata. Queries gain a `lang` parameter. Figures stay where
  they are (`product_facet` values are language-free); only labels translate.
- **Entities with one row and a slug get an `_i18n` sidecar**:
  - `product_category_i18n(category_id, lang, slug, name, h1, seo_title, meta_description,
    intro_md, image alts)`
  - `product_i18n(product_id, lang, name, seo_title, meta_description, intro_md, best_for)`
  - `store_i18n` for any description text
  
  English stays on the base row, so nothing English moves.
- **Articles**: already one row per language with `lang` (added 2026-10-03). Add
  `translation_key` to group the three versions. Localised `path` for `ms`
  (e.g. `ms/panduan-membeli/hood-dapur`). Article paths become locale-prefixed for non-English.
- **UI strings**: `src/i18n/{en,ms,zh}.ts`, typed against the English file so a missing key
  fails `tsc`. A `t(locale)` helper. This replaces the `UI` object in the article page and
  the `label`/`lang` props on `CtaBar`. WhatsApp prefill text (`whatsappLink`,
  `enquiryMessage`) is localised too.
- **Keyword map**: `data/sql/keyword-map.sql`, one row per (page, lang): primary keyword,
  volume, source, pulled date, and basis (`volume` or `competitor`). Every translated
  title, H1, meta and Malay slug cites its row. This is the record that the brief was
  followed.

### SEO plumbing

- `alternates.languages` on every page: `en-MY`, `ms-MY`, `zh-Hans-MY`, `x-default` → English.
  It lists only the translations that exist, so a page in rollout never points at a 404.
- Sitemap: one entry per URL with `alternates.languages` (Next's sitemap supports it). The
  hardcoded `ORIGIN`s (sitemap.ts:25 and five page files) are replaced with `SITE_ORIGIN`
  from `src/lib/deployment.ts` while we are in there.
- JSON-LD: `inLanguage` on every node that takes it; breadcrumb names from the dictionary.
- OG `locale` per page.
- A language switcher in `SiteHeader` that links to the current page's own translation
  (falling back to the locale home).
- CJK font fallback (`:lang(zh)` stack: PingFang SC, Microsoft YaHei, Noto Sans SC).
- Number and date formatting via the locale (`formatDate` already takes one).

### Checks

- `db-check` additions:
  - Localised slug uniqueness per locale.
  - Every `_i18n` row's base exists.
  - Internal links in `ms`/`zh` content resolve within their locale.
  - The existing hand-authored-link check extended to translated rows. **Also fix its redirect
    branch, which never matches**: from_path is stored `/x/`, and the check strips to `x`.
  - A coverage report (counts per locale), informational during rollout.
- New `scripts/i18n-check.mjs <base>`: fetch the sitemap, assert every URL is 200 and every
  hreflang set is reciprocal.
- `urls:check` is unchanged and still gates the legacy contract.

## Size, and what is not translated

Measured from `.data/vatti.db` and the components (2026-10-03):

| Area | Words per language |
|---|---|
| Articles (105 published: 26 buying guides, 53 tips, 26 recipes) + titles/meta | ~90,000 |
| Products (36 published): intro, 322 features, 230 FAQs, spec lines, dimension labels | ~33,500 |
| Categories (5): copy + 30 guides, 30 reasons, 50 FAQs | ~6,000 |
| Recipes (16): ingredients, steps | ~3,500 |
| Image alt text | ~3,000 |
| Hardcoded UI (~600 strings across ~30 files) | ~6,000 |
| **Total** | **~142,000 per language, ~285,000 for both** |

Not translated, on purpose:
- `product_image.caption_md` (11,500 words). It renders only when a product has no
  feature rows, and no published product is in that state.
- Google reviews. They are customer quotes; they render with `lang="en"`.
- Dealer names and addresses, warranty dealer names, partner names, model codes and
  series names.

At this size translation runs as batches across sessions. One SQL file per batch
(`data/sql/i18n-<lang>-<area>-<n>.sql`), each self-contained and shippable, so a stopped
session never leaves a half-translated page live: a page appears in a locale only when
its rows exist.

## Pitfalls the inventory turned up

- **Fonts are Latin-only** (Geist, `subsets: ["latin"]`). Chinese needs a CJK system-font
  fallback under `:lang(zh)`, or it renders in whatever the browser picks.
- **Archives already leak.** `/category/buying-guide/` lists the two Malay guides among the
  English ones. Archive queries take `lang`, and each locale gets its own archive.
- **Generated English in queries.** Filter labels, bands and superlatives are built as
  strings in `src/lib/queries/category.ts` ("Under {n}", "Quietest", "Ductless capable").
  `warrantyLine()` assembles English grammar ("x, y and z"). These move to the dictionaries,
  with a list-join per locale (Malay "dan", Chinese 、 and 和).
- **The enquiry funnel copies the visitor's answers into the WhatsApp message**
  (`src/components/enquiry.ts`). The visitor writes in their own language, so the message
  arrives in it, which suits a conversation. The fixed opening line ("Hi VATTI Malaysia")
  is localised too.
- **Numbers** are hard-wired to `toLocaleString("en-MY")` (`fmt`, `formatValue`, `mm`), so
  these take the locale.
- **Hardcoded origins** (`sitemap.ts:25`, `[slug]/page.tsx:232`, `[article]/page.tsx:262`,
  `CategoryView.tsx:1035`, `page.tsx:186`, `store/[slug]`) are replaced by `SITE_ORIGIN`
  so locale URLs are built in one place.
- **Products barely need their own keyword research.** Model codes are language-free; a
  product page targets the category term in each language plus the model. So the keyword
  map is mostly categories (5 × 2), home, static pages and articles (105 × 2).

## Rollout

0. **Keyword map**: research each page × language before writing it (Ubersuggest MY ms/zh,
   Firecrawl SERP from KL; competitor terms where volume is absent).
1. **Infrastructure**: route groups, views, dictionaries, schema columns, hreflang, sitemap,
   switcher, checks. Move the two Malay guides to `/ms/` with 301s. Ship with English-only
   behaviour unchanged.
2. **Money pages**: home, 5 categories in `ms` and `zh`, plus English and Chinese counterparts
   of the two Malay guides.
3. **Products**: all published products (intro, features, FAQs, spec labels, dimensions).
4. **Articles** by organic clicks, highest first.
5. **Static pages, store template, recipes, eWarranty form.**

Each phase ships on its own, with `db-check`, `urls:check` and `i18n-check` green before push.
